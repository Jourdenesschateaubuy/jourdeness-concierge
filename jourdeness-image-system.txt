JOURDENESS MEDIA SYSTEM
Current Production Architecture
Updated: 2026-09-25

==================================================
1. PURPOSE
==================================================

This document describes the current Jourdeness media architecture.

The previous local /api/uploads product-image pipeline has been retired.
Production media delivery now uses Cloudflare R2.

==================================================
2. SOURCE OF TRUTH
==================================================

NAS
- NAS is the master/source-of-truth for Media Library files.
- Original media files remain on NAS/local storage.
- media_assets.storage_path must continue to represent the NAS/local source path.
- Never replace storage_path with an R2 URL.

Neon
- Neon stores media metadata, database references, and publish-job status.
- Neon does not replace NAS as the original file source.

Cloudflare R2
- R2 stores published copies used by the production website.
- Bucket: jourdeness-media
- Worker binding: JOURDENESS_MEDIA
- R2 object key format:

  media/{media_id}

Example:

  media/119

==================================================
3. MEDIA PUBLISH FLOW
==================================================

Normal production flow:

NAS
  |
  v
Media Library / Neon
  |
  v
media_publish_jobs
  |
  v
Media Publisher
  |
  v
Cloudflare R2
  |
  v
Cloudflare Worker
  |
  v
Production Website

Publish job statuses:

- pending
- processing
- published
- failed

Main publisher scripts:

- scripts/run-media-publisher.ts
- scripts/publish-media-by-id.ts

The Windows scheduled task runs the publisher periodically:

- Jourdeness Media Publisher

==================================================
4. PUBLIC MEDIA DELIVERY
==================================================

Production media is served through:

  /api/studio/media/{id}/file

Example:

  /api/studio/media/119/file

The Cloudflare Worker reads:

  R2 key: media/{id}

The Worker handles GET and HEAD requests and streams the object from R2.

The R2 bucket remains private.
The public website does not need a public R2 bucket URL.

==================================================
5. PRODUCT AND CMS IMAGE REFERENCES
==================================================

New product/CMS media should use Media Library references.

Preferred production URL format:

  /api/studio/media/{id}/file

Product images, Bundle Offer images, and Website Studio images should use
the Media Library instead of the retired direct-upload pipeline.

==================================================
6. CLEANUP FLOW
==================================================

Media cleanup uses the cleanup queue/system.

Before physical deletion, Usage Guard checks whether the media is still used
by relevant database records.

Cleanup behavior:

- Validate media state.
- Check usage references.
- Delete R2 object.
- Delete NAS source only when allowed.
- Update database state safely.

R2 deletion is treated as idempotent.

Main cleanup script:

- scripts/cleanup-media-by-job.ts

NAS deletion must remain confined to the configured upload/source root.

==================================================
7. IMPORTANT INVARIANTS
==================================================

DO NOT:

- overwrite media_assets.storage_path with an R2 URL
- make R2 the master/original storage
- restore the old /api/uploads product-image pipeline
- restore direct product-image upload routes
- bypass Media Library for new production media
- delete NAS media without Usage Guard / cleanup validation

KEEP:

- NAS as source of truth
- Neon as metadata/job state
- R2 as production published copy
- Worker as public delivery layer
- R2 key format media/{id}

==================================================
8. RETIRED LEGACY IMAGE SYSTEM
==================================================

The following legacy runtime paths/components have been retired:

- /api/uploads/*
- /api/admin/product-images/upload
- lib/upload-storage.ts
- lib/media-url.ts
- saveProductImage()
- deleteUploadedImage()

Do not reintroduce them unless the media architecture is intentionally
redesigned and reviewed.

==================================================
9. CLOUDFLARE PRODUCTION BINDINGS
==================================================

Current important bindings:

- JOURDENESS_MEDIA
  Type: R2 Bucket
  Bucket: jourdeness-media

- VINEXT_KV_CACHE
  Type: KV Namespace
  Purpose: vinext persistent cache / ISR support

Cloudflare secrets include production application secrets such as:

- DATABASE_URL
- ADMIN_PASSWORD

Secret values must never be committed to Git or written into this document.

==================================================
10. PRODUCTION WORKER
==================================================

Production Worker:

  jourdeness-concierge

Current production host:

  https://jourdeness-concierge.jourdeness-dev.workers.dev

The old Vercel hostname is retained only as a redirect entry point and
redirects requests to the Cloudflare Worker.

==================================================
11. MAINTENANCE RULE
==================================================

If the media architecture changes, update this document in the same Git
change so this file remains an accurate description of production.
